# Skill: Extract IR Files for a Failing Test

How to capture the intermediate-representation artifacts that let
`failure-investigator` trace a failure to its root cause.

For human-readable detail, see
`instructions/debug-ir-files.txt`.

## What to Extract

For every investigation, capture three artifacts:

1. **The kernel's `.ttadapter` file** — produced by the Triton frontend.
   This is the input to `bishengir-compile`. Found in the Triton cache at
   `/root/.triton/cache/<hash>/<kernel>.ttadapter`.
2. **A full pass-by-pass IR dump** — generated by re-running
   `bishengir-compile` on the `.ttadapter` with `--mlir-print-ir-after-all`.
3. **The failure-mode marker** — for SEGV, the address; for ACCURACY, the
   max diff vs CPU; for COMPILE failures, the exact pass and error.

## Storage Convention

```
state/tasks/<task>/issues/<category>/
  README.md                  # one paragraph: what's in this folder
  representative-test.txt    # full pytest test name
  <kernel>.ttadapter         # input IR
  full-dump.log              # --mlir-print-ir-after-all output
  failure-marker.txt         # the actual error/diff/address
```

On `A5 primary`, the same artifacts are mirrored under
`<pipeline_root>/dt_debug_master/gen_ir/<category>/` so master-maintainer
can re-extract during regression runs.

## Procedure

### 1. Find the kernel cache for a failing test

Run the test once to populate the Triton cache:

```bash
ssh npu-user@a5-primary.example.org "
  docker exec ascend_test_env bash -c '
    source /home/npu-user/permanent_pipeline/scripts/setenv.bash
    rm -rf /root/.triton/cache/*
    cd /home/npu-user/permanent_pipeline/triton_ascend/test/flaggems_cases/repo
    pytest <test_name> --ref cpu -sv 2>&1 | tail -50
    # The cache is now populated; identify the kernel hash:
    ls /root/.triton/cache/
  '
"
```

For each cache subdirectory, the `.json` file lists the kernel name so you
can identify the right one:

```bash
docker exec ascend_test_env bash -c '
  for d in /root/.triton/cache/*/; do
    echo "=== $d ==="
    cat $d/*.json | python3 -m json.tool | head -5
  done
'
```

### 2. Pull the .ttadapter to the local investigation folder

```bash
mkdir -p state/tasks/<task>/issues/<category>
ssh npu-user@a5-primary.example.org "
  docker exec ascend_test_env cat /root/.triton/cache/<hash>/<kernel>.ttadapter
" > state/tasks/<task>/issues/<category>/<kernel>.ttadapter
```

### 3. Generate the full pass dump locally

Inside the `ascend-build` container so the right binary is used:

```bash
docker cp state/tasks/<task>/issues/<category>/<kernel>.ttadapter \
    ascend-build:/tmp/

docker exec -w /tmp ascend-build bash -c "
  /src/master/AscendNPU-IR-Dev/build-master/bin/bishengir-compile \
    /tmp/<kernel>.ttadapter \
    --target=Ascend950PR_957c \
    --enable-hfusion-compile=true \
    --enable-triton-kernel-compile=true \
    --enable-auto-bind-sub-block=true \
    --enable-vf-merge-level=1 \
    --mlir-disable-threading \
    --mlir-print-ir-after-all \
    -o /tmp/out.o 2> /tmp/full-dump.log
  echo exit=$?  # exit=1 with 'Cannot find hivmc-a5' is OK — IR dump is still valid
"
docker cp ascend-build:/tmp/full-dump.log \
    state/tasks/<task>/issues/<category>/full-dump.log
```

Notes:

- The compile may exit with `[ERROR] Cannot find hivmc-a5 under $PATH` —
  this is fine. The MLIR passes ran to completion and `full-dump.log` is
  valid through `inject-ir`.
- For SIMT-path kernels (`force_simt_only=True`), use the `.ttir` instead
  of `.ttadapter` and add `--pure-simt --use-dpx --num-warps=32
  --threads-per-warp=32 --enable-bishengir-simt-optimization=111`.

### 4. Find the failing pass

In `full-dump.log`:

```bash
grep -n "IR Dump After" state/tasks/<task>/issues/<category>/full-dump.log
# Find the last successful pass; the failure is in the next one.
```

For RUNTIME failures (no compile error), there is no failing pass — the IR
all builds, but the resulting binary misbehaves. In that case, diff the IR
against a working reference (e.g., the same test on stock `dev_reference`).

### 5. Trace to root cause

- Walk backward from the failing pass: which IR pattern triggers the
  failure? What's the source of that pattern?
- For ACCURACY: bisect the IR — re-compile starting from each pass dump and
  see where the result starts diverging from CPU reference.
- For SEGV/illegal: cross-reference the kernel name in the binary's symbol
  table with the `inject-ir` IR to pinpoint which kernel and which
  vector op crashed.

## Capturing LLVM IR (post-MLIR, before bisheng)

When the MLIR pass dump shows the FINAL MLIR is identical between
passing and failing builds, the bug is downstream — in MLIR→LLVM-IR
translation or LLVM optimization, both of which happen inside
`bishengir-compile-a5` before `bisheng` consumes the result.

Capture the LLVM IR by wrapping `bisheng`:

```bash
# inside the container that runs the test
cat > /dev/shm/wrap_bisheng.sh <<'EOF'
#!/bin/bash
LOG=/dev/shm/dts_capture/bisheng.log
mkdir -p /dev/shm/dts_capture
{
  echo "--- $(date +%H:%M:%S.%N) PID=$$ ---"
  echo "argc=$#"
  i=0
  for a in "$@"; do
    echo "  argv[$i]=[$a]"
    if [ -f "$a" ]; then
      cp "$a" "/dev/shm/dts_capture/${i}_$(basename $a)" 2>/dev/null || true
    fi
    i=$((i+1))
  done
} >> "$LOG"
exec /data/pri/Ascend/9.1.0.B010/cann-9.1.0/bin/bisheng "$@"
EOF
chmod +x /dev/shm/wrap_bisheng.sh

mkdir -p /dev/shm/wrap_bin
ln -sf /dev/shm/wrap_bisheng.sh /dev/shm/wrap_bin/bisheng

# Prepend to PATH so bishengir-compile picks up the wrapper:
export PATH=/dev/shm/wrap_bin:$PATH
```

Now re-run the failing test. The capture dir holds:

  - `0_kernel_mix_aic.ll` — cube-core LLVM IR
  - `0_kernel_mix_aiv.ll` — vector-core LLVM IR
  - `9_meta_op.aic.c310.bc`, `19_libdevice.10.bc`, etc. — bitcodes

Run again with the passing binaries, save to a different capture dir,
then `diff` the `.ll` files. The first diverging instruction is the
codegen bug. Common patterns:

- **Misordered instructions**: an op that defines a value moved past a
  use, so the use sees a stale prior value (predicate, address, etc.).
- **Missing/duplicate intrinsic calls**: a pass deleted or duplicated
  an `llvm.hivm.*` call.
- **Wrong predicate width**: `pge.b32(N, ...)` with the wrong N.

`bisheng` is invoked once per core (mix_aic, mix_aiv). For mix-mode
kernels, the bug usually lives in only one of the two — diff each
separately to narrow.

## Pass Names — Common Reference

| Pass | What it does | Common bug locations |
|---|---|---|
| `ConvertArithToHFusion` | i1 extui patterns | i1 conversion bugs |
| `LegalizeBoolPass` | tensor i1 → i8 at boundaries | only handles device entry |
| `OutlineVectorFunction` | creates VF functions | i1 may cross boundary here |
| `AutoVectorizeV2` | tile + vectorize linalg | rank-0 tensor crashes |
| `ConvertHFusionToHIVM` | tensor → memref + HIVM ops | type conversion bugs |
| `PlanMemory` | UB allocation | size calc bugs (sub-byte types) |
| `AllocToPointerCast` | alloc → pointer_cast | concrete UB offsets |
| `inject-ir` | final IR before hivmc | last chance to widen / fix |

## Cleanup

After investigation, the `state/tasks/<task>/issues/<category>/` folder is kept
in git for future reference. Large `full-dump.log` files (>10 MB) are
gitignored — list their sha256 in `state/tasks/<task>/issues/<category>/README.md`
so they can be regenerated.
